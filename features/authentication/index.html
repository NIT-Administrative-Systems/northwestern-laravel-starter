Authentication

The Northwestern Laravel Starter provides a multi-method authentication system that handles Northwestern users (via NetID/SSO) and external collaborators (via passwordless verification codes), and integrations through OAuth credentials issued by Laravel Passport.

Authentication Methods

Section titled “Authentication Methods”

NetID Single Sign-On

Northwestern SSO (Entra ID or Online Passport)

Primary authentication method for Northwestern users via NetID.

  • Entra ID (OAuth2) or Online Passport (cookie-based)
  • Multi-factor authentication support
  • Automatic user provisioning
  • Session-based authentication

Passwordless Verification Codes

Email OTP Authentication

Email-based passwordless authentication for external users.

  • No password management
  • Time-limited verification codes
  • Rate limiting protection
  • Invite-only access

OAuth Clients

Laravel Passport

Client credentials for integrations, which get short-lived access tokens.

  • Multiple clients per API user
  • IP allowlisting
  • Expiring, rotatable secrets

Signing In

Section titled “Signing In”

Sign-in belongs to the App panel. Guests who open a page in any panel are sent to /app/login, headed “Sign In to” and the application’s name, which lists the sign-in methods this application has configured:

  • Sign In with NetID appears when single sign-on is configured. It uses Online Passport (WebSSO) when that is configured, otherwise Entra ID.
  • Sign In with Email appears when LOCAL_AUTH_ENABLED=true. It is the secondary button beside NetID, and the primary one when it is the only method. Outside production, a note under it then says NetID sign-in isn’t set up in that environment.
  • Sign In As appears in the local environment only. See Signing In Locally.
  • If none is available, the page explains that no sign-in methods are available.

When NetID is the only method, /app/login skips the page and goes straight to single sign-on. The exceptions are the ci environment, where the page always renders so end-to-end tests can sign in with email codes, and local, where it offers Sign In As.

Email sign-in is a single page, /app/login/email, with two steps: request a code, then enter it. Progress is kept in the session, so reloading the page returns to the current step.

Which methods are offered, and the step every method ends with, are decided in App\Domains\Auth\SignIn. Every sign-in finishes with SignIn::complete(): a new session and CSRF token, a login record, and the page the person asked for, or /. An email code sign-in is remembered past the session (Laravel’s remember cookie), since a new code costs a trip to the inbox; single sign-on and Sign In As aren’t, since signing in again is usually silent or one click. SignInMethod::remembers() is where to change that.

Signing In Locally

Section titled “Signing In Locally”

A local environment needs no SSO, email or credentials to sign in. In the local environment, the sign-in page has a Development section with a Sign In As… menu of the seeded demo users, each shown with its role:

UserSigns in as
nuit.adminNUIT Administrator, a Super Administrator
generic.userA Northwestern user with no extra roles
partner.userA local (email) account, when LOCAL_AUTH_ENABLED=true

Each menu item is a link to /app/login/as/{username}, which signs in as that user, records the sign-in like any other, and redirects to / (or the page you asked for). Agents and scripts can use the URL directly, at any host or port the application is served on.

The users come from DemoUserSeeder, which db:rebuild runs. Add the users you seed for specific roles to its SIGN_IN_AS list and they appear here too. API users can’t be signed in as.

Caution

The route is registered only when APP_ENV=local: an explicit check for local, not “anything but production”. It doesn’t exist in ci, develop, qa, production or any other environment, and the controller refuses outside local as well.

To test real NetID sign-in locally, configure Entra ID or Online Passport (see Installation). The Azure redirect URI must match the host you use.

Where Users Land After Signing In

Section titled “Where Users Land After Signing In”

Every sign-in path ends at /. HomeController shows guests the landing page and sends signed-in users to destinationFor(), which returns the App panel by default. A user who started from a specific page, for example a link in an email, is returned to that page instead.

To change where signed-in users go, override destinationFor():

  • Per role
  • No landing page

To send guests straight to sign-in instead of showing the landing page, replace the return view('public.landing'); that ends __invoke():

NetID Authentication

Section titled “NetID Authentication”

Northwestern users authenticate via single sign-on using their NetID credentials. The starter supports two SSO providers, Microsoft Entra ID (OAuth2) and Online Passport (agentless WebSSO via ForgeRock), and auto-detects which one to use based on your configured credentials. See the WebSSO / Entra ID documentation for provider-specific details.

How It Works

Section titled “How It Works”

  1. User visits protected route

    User attempts to access a route requiring authentication

  2. Redirect to SSO

    The application sends the guest to /app/login. When email sign-in is off, that page redirects straight to Northwestern’s authentication service; otherwise the user picks Sign In with NetID there

  3. User authenticates

    User enters NetID and password (+ MFA if enabled)

  4. Callback with token

    SSO provider redirects back with authentication token

  5. User provisioning

    Application creates/updates user record from Directory Search data

  6. Session established

    SignIn::complete() signs the user in and starts a new session

User Provisioning

Section titled “User Provisioning”

When a Northwestern user signs in for the first time, the application:

  1. Validates NetID from SSO response
  2. Queries Directory Search API for user demographics
  3. Creates user record with demographic data:
    • Full name
    • Email address
    • Department
    • Affiliations (student, faculty, staff, etc.)
    • etc.

Later sign-ins update the user’s demographic data to keep it synchronized. If Directory Search can’t be reached, someone who already has an account signs in with the details already stored, and someone signing in for the first time sees the 503 page after three attempts. A lookup never reactivates a deactivated account. See Directory Search.

Passwordless Verification Codes

Section titled “Passwordless Verification Codes”

External users (non-Northwestern) can access the application via time-limited verification codes sent to their email.

How It Works

Section titled “How It Works”

  1. Admin creates local user

    Administrator creates a local user account in the Filament panel

  2. Verification code sent

    The user requests a code on /app/login/email, or a super administrator (ManageAll) sends one with Send Verification Code on the user’s page (or the Send a verification code now option when creating the user)

  3. User receives email

    The email contains the code (valid for 10 minutes by default, LOCAL_AUTH_CODE_EXPIRES_MINUTES) and an Enter your code button. The button opens /app/login/email at the code step for that challenge, so a code sent by an administrator or read on another device can be entered. The link alone does not sign anyone in, and an expired, used, locked or altered link is ignored.

  4. User enters code

    On /app/login/email, the code authenticates the user and SignIn::complete() establishes a session

  5. Code expires

    Code becomes invalid after use or expiration

Configuration

Section titled “Configuration”

Tip

Setting LOCAL_AUTH_USE_FIXED_CODE=true in your local .env replaces random verification codes with a fixed, predictable code (e.g. 123456 for a 6-digit code). This avoids checking your mail trap every time you sign in during development. It works only when APP_ENV is local, testing or ci. In any other environment the application refuses to boot with it turned on, so a deployment that sets it fails at once.

Creating Local Users

Section titled “Creating Local Users”
  • Via Administration Panel
  • Programmatically
  1. Navigate to Users
  2. Click Add User → Add Local User
  3. Enter the email address, first and last name, job title and organization (all required), and an optional description
  4. Select Send a verification code now if the user is ready to sign in. Otherwise they can request one themselves.
  5. Create the user

CreateLocalUser generates a unique username and creates the local user as an affiliate. Only the email is required; the other details are optional. With sendLoginLink: true (the default), it also emails a verification code.

To give a role to many people at once, local accounts included, use Add People to a Role on the Users list or a role’s Assigned Users tab. See Adding People in Bulk.

Security Features

Section titled “Security Features”

Time-Limited Codes

Codes expire after LOCAL_AUTH_CODE_EXPIRES_MINUTES (default: 10 minutes)

Single-Use Codes

Each code can only be used once, preventing replay attacks. A new code ends the earlier ones for that email, so only the latest works

Daily Guess Limit

An email can enter LOCAL_AUTH_CODE_MAX_FAILED_PER_DAY incorrect codes (default: 20) across all its codes before it waits out the day

Rate Limiting

Limits sign-in code requests to prevent abuse and enumeration attacks

Timing Attack Protection

Consistent response times prevent user enumeration via timing analysis

Deactivating Accounts

Section titled “Deactivating Accounts”

An administrator with EditUsers deactivates someone with Deactivate on their page in Administration. App\Domains\User\Actions\Lifecycle\DeactivateUser:

  • soft-deletes the account, so it can’t sign in and drops out of the Users list (the Trashed filter finds it),
  • revokes their personal access tokens, connected applications and service clients with RevokeAllCredentials,
  • signs them out everywhere with App\Domains\Auth\Actions\EndSessions, which deletes their rows from the sessions table and cycles their remember token, and
  • records an Account Deactivated audit event.

Reactivate (ReactivateUser) restores the account and records Account Reactivated. The credentials revoked with it stay revoked.

Only Reactivate brings an account back. A deactivated person who signs in, with a NetID or any other method, is refused by SignIn::complete() and sees a page saying their account is deactivated and to contact the team that supports the application. Looking them up in the Northwestern Directory, whether at sign-in, from Add Northwestern User or the directory sync on their page, updates their details and leaves them deactivated. Add Northwestern User sends you to their page to reactivate them, and adding people in bulk lists them as not added.

A session that signed in before the account was deactivated stops working too: User::canAccessPanel() refuses both panels to an account that is deleted or whose NetID is inactive, so its next request is refused.

Nobody deactivates or reactivates their own account, and nobody does either while impersonating, super administrators included. App\Domains\User\AccountStatusAccess decides both.

When EventHub reports a NetID deactivated, deprovisioned or on security hold, ProcessNetIdUpdate ends that person’s sessions the same way. See EventHub.

Expiring Local Accounts

Section titled “Expiring Local Accounts”

Set LOCAL_ACCOUNT_INACTIVITY_DAYS to deactivate local accounts nobody has signed in to for that many days. The daily users:deactivate-inactive-local command finds them from the sign-in records, and gives a new account the same time for its first sign-in. Reactivating an account counts as a sign-in, so a reactivated account gets the full time again. Northwestern accounts are left to the NetID lifecycle. It’s off by default.

Keep sign-in records long enough

The last sign-in comes from the sign-in records and the last reactivation from the audit log, so keep LOGIN_RECORD_RETENTION_DAYS and AUDIT_RETENTION_DAYS at least as long as LOCAL_ACCOUNT_INACTIVITY_DAYS. Otherwise someone whose last sign-in or reactivation was pruned looks inactive.

API Authentication

Section titled “API Authentication”

Integrations authenticate as API users through OAuth service clients issued by Laravel Passport.

How It Works

Section titled “How It Works”

  1. Admin creates an API user and a client

    An administrator creates an API user with its first service client, or adds a client to an existing API user

  2. Credentials delivered once

    The client ID and secret are shown only at creation; the secret is stored hashed and can’t be retrieved again

  3. Client gets an access token

    The integration exchanges the client ID and secret at POST /oauth/token for an access token that lasts one hour

  4. Token in requests

    The integration includes the access token in the Authorization: Bearer header

  5. Middleware validates

    AuthenticatePassportToken validates the token, the client’s secret expiry and IP allowlist, and authenticates the request as the client’s API user

  6. Request logged

    API request logged with metrics and analytics

See the API Documentation for complete client management details.

User Segmentation

Section titled “User Segmentation”

Every sign-in creates a UserLoginRecord with a segment, a classification of the user at that moment. Segments feed the Sign-In Records page in the administration panel (charts, stats, filters) and are captured at sign-in so historical metrics stay accurate when roles change later.

Sign-in records are deleted after LOGIN_RECORD_RETENTION_DAYS (default 365). See Data Retention.

Rate Limiting

Section titled “Rate Limiting”

Authentication uses layered rate limits to prevent brute force attacks and abuse. Limits are applied per IP and per identifier (email or challenge ID) to balance security with usability. App\Domains\Auth\LoginCodes enforces the passwordless limits itself, along with the resend cooldown, because the email sign-in page’s Livewire actions don’t pass through route middleware.

Impersonating Users

Section titled “Impersonating Users”

Users with the ManageImpersonation permission can sign in as another user to see the application as they do. The Impersonate button on a user’s page in the administration panel posts to /impersonate/take/{id} and opens the app panel as that person, since the page you came from is usually one they can’t open. API users can’t be impersonated, and neither can a deactivated account or one whose NetID is inactive (canBeImpersonated() in HandlesImpersonation). Nor can someone who holds a permission the impersonator lacks, whether it comes from a role or was given directly, since acting as them would lend the impersonator that permission. ManageAll counts as every permission, so a user who has it may impersonate anyone the earlier rules allow.

While impersonating, both panels show the theme’s impersonation banner, whose leave button posts to /impersonate/leave and returns to the original account, on the page where impersonation started. Both routes are in routes/auth.php and share the impersonation rate limit.

Each start is recorded in the impersonation log, which is kept forever unless IMPERSONATION_LOG_RETENTION_DAYS is set. See Audit Logging.

For information on roles, permissions, and policies after a user is authenticated, see the Authorization documentation.
